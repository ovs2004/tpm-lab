# Требования TPM Lab

**Версия:** 0.1  
**Статус:** baseline для уточнения на неделе 2

Требования описывают ожидаемый финальный проект. Они не означают, что функции уже реализованы. В Sprint 01 проверяется только полнота и согласованность документации.

## Функциональные требования

### FR-01 — TPM discovery

- **Описание:** система должна обнаружить доступный TPM 2.0 через настроенный TCTI и отличить успешное соединение от отсутствия/недоступности TPM.
- **Метод проверки:** запустить discovery check; подтвердить реальный успешный TPM command либо ожидаемый non-zero exit и диагностическое сообщение при отключённом интерфейсе.
- **Целевой milestone:** неделя 7, Demo 1.

### FR-02 — Чтение TPM capabilities

- **Описание:** система должна запросить у TPM его properties/capabilities, достаточные для идентификации TPM 2.0 и используемой конфигурации.
- **Метод проверки:** выполнить capability query и проверить структуру реально возвращённых полей, не сравнивая их с вымышленным заранее записанным выводом.
- **Целевой milestone:** неделя 7, Demo 1.

### FR-03 — Чтение PCR

- **Описание:** система должна читать выбранный PCR и сохранять его значение до операции измерения.
- **Метод проверки:** выполнить PCR Read, проверить exit code, номер PCR, hash algorithm и корректный формат digest.
- **Целевой milestone:** неделя 8, Demo 2.

### FR-04 — PCR Extend

- **Описание:** система должна вычислить deterministic measurement, выполнить реальный `PCR Extend` и подтвердить изменение выбранного PCR.
- **Метод проверки:** прочитать PCR до и после `Extend`; независимо вычислить ожидаемый digest по правилу `newPCR = Hash(oldPCR || measurementDigest)` и сравнить.
- **Целевой milestone:** неделя 8, Demo 2.

### FR-05 — Создание TPM-backed key

- **Описание:** система должна создать key object, private material которого управляется TPM и не используется приложением как обычный plaintext private-key file.
- **Метод проверки:** создать и загрузить object, прочитать public area и успешно выполнить с ним TPM operation; документировать созданные public/private object blobs без заявления об аппаратной защите `swtpm`.
- **Целевой milestone:** неделя 9.

### FR-06 — Подпись TPM-backed key

- **Описание:** система должна передать digest/data в TPM software stack и получить подпись от загруженного TPM-backed signing key.
- **Метод проверки:** подписать deterministic input реальной TPM-командой/API, проверить exit code и наличие непустой подписи правильного формата.
- **Целевой milestone:** неделя 10, Demo 3.

### FR-07 — Проверка подписи

- **Описание:** система должна проверить подпись соответствующим public key и отклонить изменённые data или signature.
- **Метод проверки:** positive verification завершается успешно; отдельная negative verification после изменения input завершается ожидаемым отказом.
- **Целевой milestone:** неделя 10, Demo 3.

### FR-08 — Sealing секрета

- **Описание:** система должна создать TPM object с учебным secret и policy, связанной с известным PCR state.
- **Метод проверки:** создать policy/object реальными TPM operations, проверить exit codes и наличие необходимых object artifacts; plaintext secret не выводить без необходимости.
- **Целевой milestone:** неделя 11, Demo 4.

### FR-09 — Unseal при корректной policy

- **Описание:** система должна возвращать исходный secret, когда текущий PCR state удовлетворяет policy.
- **Метод проверки:** выполнить policy session и `Unseal`; побайтово сравнить результат с deterministic test secret.
- **Целевой milestone:** неделя 11, Demo 4.

### FR-10 — Отказ Unseal после изменения PCR

- **Описание:** после реального изменения policy-bound PCR операция `Unseal` должна быть отклонена TPM policy validation.
- **Метод проверки:** выполнить `PCR Extend`, подтвердить изменение PCR, затем ожидать non-zero result/TPM policy error от `Unseal`; заранее напечатанный отказ не принимается.
- **Целевой milestone:** неделя 11, Demo 4.

### FR-11 — Демонстрация FAPI

- **Описание:** система должна выполнить выбранную security-relevant операцию через TPM2-TSS FAPI и показать используемые высокоуровневые abstractions.
- **Метод проверки:** запустить FAPI implementation против lab TPM, проверить фактический result и задокументировать lifecycle объектов/profile.
- **Целевой milestone:** неделя 13.

### FR-12 — Демонстрация ESAPI

- **Описание:** система должна выполнить ту же или эквивалентную операцию через TPM2-TSS ESAPI и показать явное управление ресурсами/session.
- **Метод проверки:** запустить ESAPI implementation, проверить фактический result и сопоставить шаги, error handling и abstraction level с FAPI.
- **Целевой milestone:** неделя 14; сравнение — неделя 15, Demo 5.

### FR-13 — Автоматизированный запуск demo

- **Описание:** единый runner должен запускать отдельные обязательные demo и их последовательность без ручной подмены результатов.
- **Метод проверки:** на чистом документированном состоянии выполнить каждый demo и `demo all`; подтвердить необходимые preconditions, cleanup и propagation exit codes.
- **Целевой milestone:** неделя 12, интегрированный MVP; расширение на неделе 15.

### FR-14 — Machine-readable PASS/FAIL

- **Описание:** каждый автоматизированный demo должен выдавать machine-readable итог `PASS` или `FAIL`, вычисленный из реальных checks; expected security rejection может давать `PASS` только после подтверждения реального отказа требуемого типа.
- **Метод проверки:** parser/тест проверяет schema и process exit code; принудительное нарушение positive и negative conditions должно переводить итог в `FAIL`.
- **Целевой milestone:** неделя 12, интегрированный MVP.

## Нефункциональные требования

### NFR-01 — Совместимость с Apple Silicon

- **Описание:** host workflow должен поддерживать macOS на Apple Silicon/ARM64 без обязательной x86 emulation.
- **Метод проверки:** пройти документированный setup на поддерживаемом Apple Silicon host и зафиксировать model/macOS/UTM/QEMU versions.
- **Целевой milestone:** недели 3–4.

### NFR-02 — Поддержка Ubuntu ARM64 guest

- **Описание:** основная guest platform — Ubuntu 24.04 ARM64; все обязательные компоненты и demo должны выполняться в ней.
- **Метод проверки:** подтвердить `aarch64/arm64`, версию ОС и запуск guest; позднее выполнить environment smoke tests.
- **Целевой milestone:** неделя 4; повторная проверка в MVP на неделе 12.

### NFR-03 — Воспроизводимость

- **Описание:** другой человек должен развернуть совместимую среду по versioned instructions и получить эквивалентные проверяемые результаты.
- **Метод проверки:** clean-room walkthrough вторым студентом с записью версий, шагов и отклонений.
- **Целевой milestone:** baseline неделя 6; полная проверка недели 12 и 16.

### NFR-04 — Понятная документация

- **Описание:** архитектура, setup, demo, limitations и troubleshooting должны быть понятны преподавателю и начинающим студентам.
- **Метод проверки:** peer review по checklist; все команды, preconditions, ожидаемые классы результата и ограничения описаны, ссылки разрешаются.
- **Целевой milestone:** непрерывно; reviews недели 6, 12 и 16.

### NFR-05 — Автоматизированная проверка

- **Описание:** критические positive и negative outcomes должны проверяться программно, а не визуальным предположением по тексту.
- **Метод проверки:** запустить test suite с исправной и намеренно нарушенной precondition; убедиться в корректных exit codes и результатах.
- **Целевой milestone:** неделя 12; расширение неделя 15.

### NFR-06 — Запрет fake/simulated success output

- **Описание:** runner не должен сообщать успех без фактической TPM/API operation и проверки её результата.
- **Метод проверки:** отключить TPM/TCTI или испортить input; любой невозможный реальный вызов обязан привести к `FAIL`, а expected negative scenario — подтвердить конкретный реальный отказ.
- **Целевой milestone:** с недели 7; release gate недели 12 и 17.

### NFR-07 — Deterministic test data, где возможно

- **Описание:** measurements, messages и учебные secrets должны быть фиксированы или генерироваться детерминированно, если случайность не является предметом проверки.
- **Метод проверки:** повторить demo после documented reset и сравнить inputs/derived expected values; TPM-generated random identifiers не считать обязательными к совпадению.
- **Целевой milestone:** недели 8–12.

### NFR-08 — Явная обработка ошибок

- **Описание:** ошибки environment, TCTI, TPM command, policy и verification должны различаться и приводить к понятной диагностике и корректному non-zero exit.
- **Метод проверки:** fault-injection checklist для отсутствующего TPM, неверного object, altered data и policy mismatch.
- **Целевой milestone:** baseline неделя 7; завершение неделя 16.

### NFR-09 — Clean reset и повторный запуск

- **Описание:** лаборатория должна иметь документированную безопасную процедуру сброса учебного состояния и повторного запуска без зависимости от скрытых artifacts.
- **Метод проверки:** выполнить reset/re-run cycle не менее двух раз и подтвердить preconditions каждого demo.
- **Целевой milestone:** неделя 12; hardening неделя 16.

### NFR-10 — Длительность classroom demo

- **Описание:** обязательный интегрированный показ должен укладываться в согласованное учебное окно; целевой автоматизированный прогон Demo 1–5 — не более 10 минут после готовности среды.
- **Метод проверки:** три timed runs на подготовленной VM; отдельно учитывать setup, объяснение и recovery.
- **Целевой milestone:** репетиция неделя 16; финал неделя 17.

## Правила трассировки и изменения

- FR/NFR должны связываться с backlog item, test/evidence и Sprint.
- Изменение target milestone или verification method проходит review второго студента.
- Статус требования становится `verified` только по сохранённому evidence реального запуска; наличие документа или planned command само по себе не является проверкой.
