# Два software TPM на ARM64

Заметка после прогона `swtpm` и `ms-tpm-20-ref` в Ubuntu 24.04 ARM64.
Команды и сырой вывод лежат в runbook, здесь только то, что из этих
прогонов следует и чего из них не следует.

Стенды:

* [swtpm](../labs/docker-arm64-swtpm.md)
* [ms-tpm-20-ref](../labs/docker-arm64-mssim.md)

## Что прогнали дважды

Оба раза один и тот же `infra/docker-tpm/run-checks.sh`.
Менялся только старт TPM и TCTI.

На reference simulator (`20261002-160428`) итог тот же, что раньше на
`swtpm`: 10 PASS / 0 FAIL. PCR 16 после Extend совпал с
`SHA256(старое значение || measurement)`, посчитанным в Python.
Подпись на изменённом сообщении вернула `0x2DB`. Unseal после смены
PCR вернул `0x99D`.

Эти три проверки как раз не про имя производителя. Формула PCR и коды
`0x2DB` / `0x99D` заданы спецификацией TPM 2.0. Если бы вторая
реализация разошлась здесь со первой, это был бы повод разбирать
стенд, а не записывать «другой vendor».

## Какие simulator вообще рядом с задачей

Их часто называют одним словом. Для лаборатории это три разные вещи.

`swtpm` вместе с `libtpms`. Это backend, который QEMU и libvirt уже
умеют подключать как virtual TPM. В Ubuntu 24.04 пакет есть и для
arm64, поэтому первый стенд ставился из apt. Протокол свой: data port
и control port, у нас `2321` и `2322`, TCTI называется `swtpm`.
В GetCapability эта сборка представляется как IBM / `SW TPM`.

`ms-tpm-20-ref`. Официальный reference code TPM 2.0, репозиторий
Microsoft, у нас commit `ee21db0a` (код версии 1.83). В Ubuntu пакета
нет, бинарник `tpm2-simulator` собран в образе. Протокол другой:
командный порт `2321` и отдельный platform-порт `2322`, TCTI
`mssim`. После запуска процесс ещё не готов к TPM-командам. Нужны
сигналы `POWER_ON` и `NV_ON`, затем `tpm2_startup -c`. В первой
попытке на platform-порт ушёл ещё `SESSION_END` (код 20). Simulator
закрыл сокет без ответа, старт упал. Для лабораторного запуска этот
сигнал не нужен, в рабочем `start-mssim.sh` его нет.

`ibmswtpm2` (`tpm_server`). Третий вариант, мы его не поднимали.
Это более старый IBM software TPM. С `swtpm` его путают из-за имени,
но по проводу он ближе к Microsoft simulator: тот же класс TCP-протокола
и тот же TCTI `mssim`. Имеет смысл только если понадобится ещё одна
независимая сборка на том же транспорте. Для virtual TPM в QEMU он
не замена `swtpm`.

QEMU в этот список не входит. QEMU не считает PCR и не проверяет
подпись. Он показывает гостю устройство и носит байты в backend.
Пока backend для этого пути у нас `swtpm`.

## Что на двух стендах реально разное

Старт. `swtpm` в нашем скрипте поднимается с
`not-need-init,startup-clear`. Reference simulator надо явно включить
и сделать Startup. Пока этого нет, `tpm2_getcap` не к чему обращаться.

Строка производителя. Reference code в этом commit отвечает
`XYZ ` (`0x58595A20`) и vendor `xCG` / `fTPM`, revision `1.83`.
Это поле сборки, не серийный номер чипа. На `swtpm` в том же поле
было IBM. Для тестов мы это поле печатаем и не используем как
условие PASS.

Откуда берётся процесс. `swtpm` ставится пакетом. Reference simulator
живёт только потому, что Dockerfile его компилирует. Повторяемость
держится на зафиксированном commit, не на версии Ubuntu.

Общее у обоих: сокет на `127.0.0.1` внутри контейнера, без `/dev/tpm0`.
Пока так, гостевая ОС «не видит TPM». Она просто клиент TCP.

устройство потом нужно в QEMU, вынесено отдельно:
[ARM64 и x86_64](arm64-vs-x86-tpm.md).
