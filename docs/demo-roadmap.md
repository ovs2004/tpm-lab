# Дорожная карта демонстраций

Документ описывает проверяемые демонстрации учебного MVP. В выводе показываются только реальные ответы команд и API. Заранее подготовленный или вручную подменённый вывод запрещён.

## Demo 1 — TPM Discovery

**Цель:** подтвердить TPM connectivity и получить capabilities, version и properties программной реализации TPM 2.0.

**Предварительные знания:** что такое guest OS, TPM, TCTI и `swtpm`; чем эмуляция TPM отличается от имитации результата.

**Вход:** запущенная Ubuntu ARM64 VM, процесс `swtpm`, настроенный TCTI и подключённый TPM endpoint.

**Ожидаемый выход:** TPM отвечает через выбранный TCTI; команды возвращают реальные capabilities, version-related properties и implementation properties.

**Условие PASS:** connectivity, capabilities и properties подтверждены успешными TPM-запросами во время показа; ошибки не скрыты, заранее записанный вывод не используется.

**Что объясняют студенты за 60 секунд:** где работает `swtpm`, как VM получает доступ к нему, почему TPM эмулируется, но команды и состояния TPM являются настоящими для этой среды.

## Demo 2 — PCR Read/Extend

**Цель:** показать, что значение Platform Configuration Register читается и предсказуемо меняется через реальную операцию `PCR Extend`.

**Предварительные знания:** PCR, hash, measurement digest и правило `newPCR = Hash(oldPCR || measurementDigest)`.

**Вход:** выбранные PCR index и hash bank, а также заранее известное тестовое измерение.

**Ожидаемый выход:** показаны значения PCR до и после `Extend`; независимо рассчитанное ожидаемое значение совпадает с новым TPM value.

**Условие PASS:** обе операции чтения и `Extend` успешны, PCR действительно изменился, а сравнение с независимо вычисленным digest прошло. Напечатанное без TPM-вызова значение считается FAIL.

**Что объясняют студенты за 60 секунд:** почему `Extend` не является обычной записью, как строится hash chain, зачем независимо вычислять ожидаемый результат и как PCR будет использован в sealing.

## Demo 3 — Ключ и цифровая подпись

**Цель:** продемонстрировать создание TPM-protected key, подпись данных и проверку подписи.

**Предварительные знания:** private key, public key, hash, digital signature; private key не должен экспортироваться в открытом виде.

**Вход:** короткий файл или строка сообщения и работающий TPM.

**Ожидаемый выход:** создан key object, сообщение подписано, проверка исходного сообщения успешна, а проверка изменённого сообщения завершается ошибкой.

**Условие PASS:** подпись создаётся во время демонстрации; исходные данные проходят verification, изменённые — нет; private key не выводится и не подменяется файловым ключом.

**Что объясняют студенты за 60 секунд:** что именно подписывается, как public key используется для verification и почему изменение сообщения ломает подпись. Private portion TPM object не используется как обычный plaintext private-key file; при этом состояние `swtpm` хранится программно и не получает аппаратной tamper resistance.

## Demo 4 — Sealing с настоящей ошибкой policy

**Цель:** доказать, что секрет можно `seal` к PCR policy и получить обратно только при совпадении состояния.

**Предварительные знания:** sealing/unsealing, PCR policy, authorization policy, зависимость доступа от измеряемого состояния.

**Вход:** тестовый секрет, выбранный PCR и policy, построенная на его текущем значении.

**Ожидаемый выход:** при исходном PCR `unseal` возвращает исходный секрет; после реального `PCR Extend` повторный `unseal` получает настоящий TPM policy error и не возвращает секрет.

**Условие PASS:** успешный и неуспешный сценарии выполняются подряд на одном sealed object; failure создаётся изменением PCR, команда завершается с ненулевым exit code или TPM error, а секрет отсутствует в failure output. Подмена ошибки текстом, скрытие exit code и заранее записанный вывод считаются FAIL.

**Что объясняют студенты за 60 секунд:** к какому состоянию привязан секрет, почему первый `unseal` успешен, какое реальное изменение нарушило policy и почему TPM отказал во втором запросе.

## Demo 5 — Сравнение FAPI и ESAPI

**Цель:** сравнить два уровня TPM2-TSS на одинаковой или явно эквивалентной security-relevant операции по фактическому поведению, а не только по теории.

**Предварительные знания:** роль TPM2-TSS, назначение FAPI и ESAPI, понятия abstraction level, object lifecycle, session и error handling.

**Вход:** одинаковые test data, согласованные параметры операции и работающая среда из предыдущих Demo.

**Ожидаемый выход:** операция выполнена отдельно через FAPI и ESAPI; сохранены реальные результаты positive и negative checks и краткое сравнение setup, lifecycle, контроля и обработки ошибок.

**Условие PASS:** оба пути действительно обращаются к TPM software stack, дают проверяемый эквивалентный security outcome, корректно обрабатывают negative case, а сравнение опирается на наблюдаемые команды, exit codes и данные.

**Что объясняют студенты за 60 секунд:** какую общую операцию сравнивали, что FAPI упрощает, чем ESAPI управляет явно, как различается error handling и почему один интерфейс не объявляется «лучше» без контекста.

## Demo 6 — Attestation / Quote (опционально)

**Статус:** не требуется для MVP и не влияет на его приёмку.

Если останется время, можно показать создание `Quote`: TPM подписывает выбранные PCR и nonce, а verifier проверяет подпись, свежесть nonce и соответствие PCR ожидаемому состоянию. Демонстрация считается дополнительной и не заменяет ни одну из Demo 1–5.
