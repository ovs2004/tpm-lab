# GitHub Projects: правила работы

Проект используется как единый видимый источник состояния работ. Каждая единица работы оформляется отдельной issue и проходит слева направо по доске.

## Колонки

### Backlog

Идеи и задачи, которые признаны полезными, но ещё не готовы к выполнению. У задачи может не быть assignee, но должны быть понятны цель и ожидаемый результат.

### Ready

Задача понятна, ограничена по объёму, имеет acceptance criteria, labels, milestone и может быть взята в работу без дополнительного уточнения.

### In Progress

Работа фактически начата. У задачи есть ровно один ответственный assignee, а описание и комментарии отражают текущее состояние.

### Review

Результат готов к проверке. В issue есть ссылка на результат, команды или шаги проверки и фактический outcome. Замечания Review остаются видимыми до исправления.

### Done

Все acceptance criteria и Task DoD выполнены, Review завершён, доказательство проверки приложено. Простое окончание работы или Sprint не является причиной перемещения в `Done`.

## Labels

Рекомендуемый базовый набор labels:

- `epic`
- `infra`
- `architecture`
- `tpm`
- `pcr`
- `crypto`
- `api`
- `testing`
- `documentation`
- `demo`
- `risk`

При необходимости команда может отдельно добавить `blocked` и priority labels, но это не должно заменять базовые labels. `blocked` сопровождается комментарием о причине и условии разблокировки.

## Прозрачность задач

Каждая Task должна явно содержать:

1. **Problem:** какую конкретную проблему решает задача.
2. **Scope:** что входит и что не входит в работу.
3. **Acceptance criteria:** проверяемый список условий результата.
4. **Assignee:** кто отвечает за доведение задачи до следующего состояния.
5. **Reviewer:** второй студент, который проверяет acceptance criteria и evidence.
6. **Labels и milestone:** область работы и плановый Sprint.
7. **Dependencies:** ссылки на блокирующие и зависимые issues либо слово `None`.
8. **Progress:** короткие фактические обновления при существенном изменении состояния.
9. **Evidence:** ссылка на код, документ, test output или demo result.
10. **Verification:** точные ручные шаги или test command и фактический результат.
11. **Closure note:** что сделано, какие ограничения остались и почему выполнен Task DoD.

Запрещены скрытые задачи «на словах». Если работа занимает заметное время или влияет на результат Sprint, она должна быть отражена отдельной issue. Если обнаружен blocker, issue остаётся в своей фактической колонке, получает `blocked`, а причина и следующий шаг записываются в комментарии.
